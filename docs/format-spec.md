## 1. 约定

- 多字节整数一律**小端**。
- 文本一律 UTF-8，不带字节序标记。JSON 按 RFC 8259。
- 时间：内部一律 UTC。JSON 里写成 RFC 3339（如 `2026-10-18T03:00:00Z`）；CRDT 文档里写成 Unix 毫秒整数。
- 条目编号：UUIDv7，文本形式为小写带连字符（`0192f3c4-7a1b-7c3d-9e8f-0123456789ab`）。
- 二进制字段在 JSON 里用标准 base64（RFC 4648 第 4 节，带填充）。
- “规范路径”：库根目录下的相对路径，`/` 分隔，只含 `[a-z0-9._-]`（见第 5.2 节）。
- 版本号：本规范整体有一个**格式版本**（`manifest.json` 的 `format_version`，当前为 1）；每种二进制封装另有自己的封装版本（第 5、12、13 节）。

## 2. 库目录结构与文件命名

```
<库根目录>/
  manifest.json                  明文，解锁所需的参数（第 3 节）
  .lock                          进程锁，防止两个进程同时打开（不同步）
  structure/
    structure.dexm               结构文档快照（第 7 节）
    structure.<设备>-<序号>.dexu  结构文档增量
  types/<h>/<类型编号>.dexm       类型定义（第 10 节），增量同上
  items/<h>/<条目编号>.dexm       条目快照（第 6、8 节）
  items/<h>/<条目编号>.<设备>-<序号>.dexu   条目增量
  logs/<种类>/<yyyy-mm>/<设备>.dexl   日志分段（第 12 节）
  blobs/<h>/<附件名>.dexs         附件（第 13 节）
  vault/                         密码库（第 16.1 节）
  local/                         只属于这台电脑，不同步（第 2.2 节）
  index.sqlite                   本地索引，可重建，不同步（第 14 节）
  tmp/                           原子写入用的临时文件，打开库时清空
```

### 2.1 命名规则

- **分片目录 `<h>`**（已确认 2026-10-18）：文件主名（条目编号、类型编号或附件名）的 UTF-8 字节做 SHA-256，取第一个字节的两位小写十六进制（`00`–`ff`）。只分一层：10 万条目时每个目录约 400 个文件，100 万条约 4000 个，都在文件系统的舒适范围内。
  - 不按编号开头分片：UUIDv7 开头是时间戳，会让同一时期的条目挤在同一个目录。
- **扩展名**：`.dexm` 快照（整体加密），`.dexu` 增量（整体加密），`.dexl` 日志分段（逐条加密），`.dexs` 附件（分块加密）。
- **设备编号 `<设备>`**：每台电脑第一次打开库时随机生成 8 字节，写成 16 位小写十六进制，存在 `local/device.json`。增量文件和日志分段都带设备编号，所以两台电脑永远不会写同一个文件，以后同步时没有文件级冲突。
- **序号 `<序号>`**：写入时的 Unix 毫秒时间，十进制；同一进程在同一毫秒内再写则加 1。这样序号永不回退、合并快照后也不会复用（以后同步时，同名文件必定是同一份内容），也不需要为每个文档另存计数器。
- 文件名只含编号、哈希、设备编号和序号，**不含标题或任何内容**。

### 2.2 只属于本机的目录 `local/`

- `local/device.json`：设备编号（用整体封装加密，路径 `local/device.json`）。
- 工作区布局、本地仓库路径等以后的本机设置，同样逐个文件整体加密。2026-11-03 加的几个：`plugin-grants.json`（启用了哪些外部插件、同意了哪些权限）、`plugin-data-<插件 id>.json`（插件自己的存储，最多 1 MB）、`scheduled-waiting.json`（定期任务没人回答的提交，只记插件或任务、请求方法和网站名）。都是本机设置，不进同步，格式版本不变。
- `local/` 和 `index.sqlite`、`.lock`、`tmp/` 一样不参与同步。
- `.lock`：进程锁，内容不读，用 `File::try_lock` 加锁（Unix 上是 flock，Windows 上是 LockFileEx 强制锁）。**不支持把库放在网络盘上**：锁和原子替换在网络文件系统上不可靠。

## 3. `manifest.json`

明文 JSON，是库里唯一不加密的文件（解锁之前必须能读到它）。

```json
{
  "format": "dem-library",
  "format_version": 1,
  "library_id": "0192f3c4-7a1b-7c3d-9e8f-0123456789ab",
  "created": "2026-10-18T03:00:00Z",
  "kdf": { "alg": "argon2id", "version": 19, "m_kib": 262144, "t": 5, "p": 4, "salt": "<16 字节 base64>" },
  "wrapped_keys": [
    { "kind": "password", "nonce": "<24 字节 base64>", "ciphertext": "<48 字节 base64>" },
    { "kind": "recovery", "nonce": "<24 字节 base64>", "ciphertext": "<48 字节 base64>" }
  ],
  "file_key_ids": [1],
  "current_file_key_id": 1
}
```

- `library_id`：创建库时随机生成（UUIDv7），之后不变。它的 16 字节形式是所有子密钥的 HKDF 盐。
- 读取时遇到不认识的字段一律保留、不报错；`format_version` 比软件支持的新时拒绝打开（不静默读错）。
- **篡改防护**：清单本身不加密，但 `kdf` 的参数、盐和 `library_id` 都绑定进了包装主密钥时的附加认证数据（第 4.3 节）。改了任何一项，解锁就会失败，而不是悄悄换成更弱的参数。

## 4. 密钥体系

```
主密码 ──Argon2id──▶ 包装密钥 ─┐
                               ├─ 解开 ─▶ 库主密钥（32 字节随机）
恢复码 ──HKDF-SHA256──▶ 包装密钥 ┘            │
                                 HKDF-SHA256（盐 = library_id 的 16 字节）
                     ┌──────────────────┼──────────────────┐
             文件密钥（带编号）    附件命名密钥          索引密钥
```

只使用 RustCrypto 的成熟实现：`chacha20poly1305` 0.10（XChaCha20-Poly1305）、`argon2` 0.5（Argon2id，版本 0x13）、`hkdf` + `sha2`（HKDF-SHA256）、`hmac` + `sha2`（HMAC-SHA256）。

### 4.1 库主密钥

- 创建库时由操作系统的安全随机数生成 32 字节。
- 日常打开：主密钥存在系统钥匙串里（macOS 钥匙串、Windows 凭据管理器，持久性为 Local），条目名为 服务 `dev.dem.desktop`（开发版用 `dev.dem.desktop.dev`，避免和正式版混用）、账户 `library:<library_id>:master`，值为 32 字节原文。读取放在后台线程并设超时；超时、被拒或读不到时退回输入主密码。
- 威胁模型补充（`docs/spikes/03-tauri-platform.md`）：Windows 上同一用户下的任何程序都能读取凭据管理器里的条目；macOS 上未签名的开发版重新构建后读取会弹出授权框。钥匙串只是免输密码的便利，不是额外的安全层。**已确认 2026-10-18**：钥匙串里存原文，不再包一层，因为钥匙串本身就是系统提供的加密存储。

### 4.2 子密钥

`HKDF-SHA256(ikm = 主密钥, salt = library_id 的 16 字节, info = 用途标签)`，输出 32 字节。

| 用途标签 | 用途 |
| --- | --- |
| `dem/v1/files/<编号>` | 文件密钥，`<编号>` 是十进制的密钥编号（当前为 `1`）。所有 `.dexm`、`.dexu`、`.dexl`、`.dexs` 都用它 |
| `dem/v1/blob-name` | 附件命名：`HMAC-SHA256(附件命名密钥, 附件明文)` 的小写十六进制就是附件名 |
| `dem/v1/index` | 索引密钥，以原始密钥形式交给 SQLCipher（`PRAGMA key = "x'…'"`，跳过它自带的 PBKDF2） |

更换文件密钥：新编号的密钥用于新写入；旧编号的文件在后台逐个重新加密后，从 `file_key_ids` 里删除旧编号。（P1 不实现，格式已预留。）

### 4.3 主密码包装

- 包装密钥 = `Argon2id(主密码的 UTF-8 字节, salt = kdf.salt, m_kib, t, p)`，输出 32 字节。
- 默认参数：`m_kib = 262144`（256 MiB）、`t = 5`、`p = 4`。在 Apple M1 上、机器较空闲时实测中位数 624 毫秒（4 轮为 502 毫秒，太贴近下限），落在计划要求的 0.5–1 秒中间。参数存在清单里，以后可以提高；已有的库沿用自己清单里的参数。
- 包装 = XChaCha20-Poly1305（密钥 = 包装密钥，随机 24 字节随机数，明文 = 主密钥）。
- 附加认证数据 = `"dem/v1/wrap/password"` ‖ `0x00` ‖ 绑定数据；
  绑定数据 = `library_id`（16 字节）‖ `m_kib`（u32）‖ `t`（u32）‖ `p`（u32）‖ `salt`（16 字节）。

### 4.4 恢复码

- 160 位随机数 + 16 位校验（SHA-256 的前 2 字节），共 22 字节，用 Crockford base32 写成 36 个字符，每 4 个一组用 `-` 分隔，共 9 组。输入时忽略大小写、空格和连字符，`I`、`L` 当作 `1`，`O` 当作 `0`；校验不对就拒绝（能发现单个字符的笔误）。
- 熵足够高，不需要慢速推导：包装密钥 = `HKDF-SHA256(ikm = 160 位随机数, salt = 空, info = "dem/v1/recovery-kek")`。
- 附加认证数据 = `"dem/v1/wrap/recovery"` ‖ `0x00` ‖ `library_id`（16 字节）。
- 忘记主密码又没有恢复码，数据无法恢复。界面在创建库时必须讲清楚，并要求确认已保存恢复码。

## 5. 小文件封装（`.dexm`、`.dexu` 和 `local/` 下的文件）

### 5.1 布局

```
偏移  长度   字段
0     4      魔数 "DEXF"
4     2      封装版本（1）
6     2      文件密钥编号
8     24     XChaCha20 随机数（每次写入随机生成）
32    n+16   XChaCha20-Poly1305 密文和认证标签
```

附加认证数据 = 头部 32 字节 ‖ `0x00` ‖ 该文件的规范路径。

- 认证头部：改版本号或密钥编号会被发现。
- 认证路径：把一个文件换到别的位置（比如把机密条目的文件改名成普通条目的）会解密失败。
- 文件改名（例如以后调整分片规则）因此必须先解密再用新路径重新加密，这属于格式迁移。

### 5.2 规范路径

- 相对于库根目录，`/` 分隔；Windows 上的 `\` 一律转换成 `/`。
- 不能为空，不能以 `/` 开头，不能有空段、`.` 段、`..` 段。
- 每段只允许 `a-z`、`0-9`、`.`、`_`、`-`。库里的文件名都是编号和哈希，所以这条规则从不误伤；只用小写也避免了大小写不敏感的文件系统把两个文件当成一个。

## 6. 条目文档

每个条目是一份 Loro 文档（CRDT 选型见 `docs/spikes/01-crdt.md`）。

### 6.1 Loro 的版本与功能限制

- Rust 核心和界面（`loro-crdt` WebAssembly）**必须使用同一版本**；当前为 1.16.x。
- 只使用 1.0 起就有的容器：`Map`、`List`、`MovableList`、`Text`、`Tree`。可合并子容器等较新的功能不用：验证发现旧版本读到它们时**不报错、静默读错**。
- 升级 Loro 版本视为格式变更：要有迁移测试，保证旧文件全部可读、新软件写的文件不会被旧软件静默读错。
- 开启提交时间记录（`set_record_timestamp(true)`），按时间查找历史版本需要它。**已确认 2026-10-18**。

### 6.2 逻辑布局

```
LoroDoc
├─ "dem"    Map   { "schema": 1 }                 文档内的逻辑版本，迁移用
├─ "meta"   Map
│    type        String   类型编号
│    title       String?  标题（可无）
│    state       String   inbox | active | archived | trashed
│    privacy     String   normal | sensitive | private | confidential
│    ai_web      Bool?    只对 sensitive 有意义：用户授权这一条可以在联网授权会话里提供给 AI；缺省为否（2026-10-19）
│    container   String?  所属领域或项目的条目编号
│    created     Int      Unix 毫秒
│    updated     Int      Unix 毫秒
│    time        String?  时间锚点的 JSON（due / span / occurred）
│    place       String?  （P4）
│    source      String   来源信息的 JSON（origin、needs_check、conflict、recheck_on、refs）；记到整篇，不记到段落（2026-11-02）
│    tags        Map<标签, true>   当集合用：两台设备并发加同一个标签不会重复
├─ "fields" Map   类型专属字段；短值直接存（标量，或字符串列表，如多选和编号列表，整体替换），长文本字段用子 Text 容器
├─ "links"  Map<关系编号, Map{ to, kind, anchor? }>   正文之外的关系（第 11 节）
├─ "body"   Map   loro-prosemirror 的结构：nodeName / attributes(Map) / children(List<Map|Text>)
└─ "labels" List<Map{ name, version, created }>     给重要版本起的名字；version 是 Loro 版本（Frontiers）的编码字节
```

- 标量字段并发修改时“较晚的为准”，被覆盖的值留在历史里，和 M10 的同步规则一致。
- `time`、`source` 存成 JSON 字符串，整体替换，不需要字段级合并。
- **正文格式**：`body` 的结构由 `loro-prosemirror` 定义，等于把这个绑定的内部结构写进了我们的格式。编辑器 schema（节点和标记的名字、属性）另写一份 `schema.json`，随代码发布并带版本号；Rust 核心和编辑器都从它生成，**格式扩展行为**（比如加粗后紧接着打的字是否加粗）也写在里面，不存进文档。
- **文档骨架只由核心创建一次**：新条目的根容器由 `dem-core` 创建并写成第一个快照；界面和其他设备一律从已有字节加载。验证发现两份副本各自初始化同一个空文档再合并会丢字或显示错乱。

### 6.3 修改来源

每次提交的提交说明记录来源：

| 提交说明 | 含义 |
| --- | --- |
| `me` | 我在界面里的修改 |
| `ai:<提议编号>` | 接受 AI 提议时应用的修改；一个提议作为**一次提交**应用 |
| `import:<批次编号>` | 导入 |
| `revert:<提议编号>` | 撤销某次 AI 修订 |
| `system` | 软件自动做的修改（如创建骨架、迁移） |

Loro 会把同一设备上连续的、提交说明相同的提交合并成一条，所以**每个提议编号、批次编号都必须唯一**。

### 6.4 编辑副本编号（peer id）

同一个编号不能被两个同时写入的副本使用。规则：每个副本（核心里打开的文档、界面编辑器里的副本）在加载文档时都取一个新的 64 位随机编号，不复用、不持久化。

### 6.5 系统条目（2026-11-03）

提议（`proposal`）、AI 会话（`ai_session`）、工作约定（`agreement`）、批注（`annotation`）、定期任务（`scheduled_task`，2026-11-03）是系统类型的普通条目，结构和其他条目一样。普通列表和搜索不显示，AI 的受限视图不把提议、会话和批注当条目给出（工作约定除外）。提议的内容放在 `fields.data`（JSON 字符串）；隐私层级等于它改的条目，所以不会把敏感内容带到更低的层级。

撤销（第 9 节）先按整条做：应用后条目没有再变过才能撤销，变过就不动并提示，不做字符级的部分撤销。

## 7. 结构文档

领域和项目的层级单独放在一份 Loro 文档里（`structure/structure.dexm`），用可移动树管理。普通条目只用 `meta.container` 记录自己属于哪个领域或项目，条目没有下级，所以不会成环。

```
LoroDoc
├─ "dem"   Map { "schema": 1 }
└─ "tree"  Tree（开启分数索引，兄弟之间有序）
     节点 meta：{ "kind": "domain" | "project", "item": 条目编号 }
```

- 领域和项目本身也是条目，名称、目标、截止时间等都在各自的条目文档里；树里只有编号和种类，没有任何内容，所以结构文档的隐私层级与普通内容相同，它本身不泄露名称。
- **并发移动**：Loro 的可移动树保证合并后仍是一棵树。验证：两台设备同时“A 移到 B 下”和“B 移到 A 下”，合并后无环；3 个副本、30 个节点、300 轮随机并发移动，0 次成环。
- **删除领域或项目**：用条目的 `state = archived`（或 `trashed`）标记，**不用树的删除操作**。原因：一边删除节点、另一边同时把节点移进来时，移进来的节点会被一起删掉。树节点只在彻底清空回收站时删除。
- 项目只能挂在领域下，领域可以挂在领域下；这一条由 `dem-core` 在移动时检查。树本身只保证无环。
- 一个条目编号在树里最多出现一次；读取时如果发现重复（并发创建造成），保留编号较小的节点，其余视为无效。

## 8. 条目文件的写入：快照与增量

**已确认 2026-10-18**：选“快照 + 增量”，不选“每次整份重写”。

- `items/<h>/<编号>.dexm`：Loro 快照（`ExportMode::Snapshot`，含完整历史），整体封装。
- `items/<h>/<编号>.<设备>-<序号>.dexu`：一批修改的增量（`ExportMode::updates`，自上一次写入后的变化），整体封装。编辑时每批修改（例如停止输入 1 秒后，或每次 AI 提议被接受时）写一个增量文件，通常一两百字节。
- **读取**：先导入快照，再按任意顺序导入同目录下所有属于这个编号的增量文件。CRDT 导入是幂等的，重复导入无害。
- **合并**：关闭条目或空闲时，导出新快照 → 原子写入 `.dexm` → 删除已经包含在新快照里的增量文件。中途崩溃最多留下多余的增量文件，下次读取时重复导入无害，下次合并时删除。
- **原子写入**：先写 `tmp/<随机名>`，写完调用 fsync，再重命名为目标文件（同一卷内），然后对目标目录 fsync（Windows 上 `MoveFileExW(MOVEFILE_REPLACE_EXISTING)`；遇到杀毒软件或搜索索引短暂占用造成的错误 5、32、33 时退避重试，5 毫秒起，最长约 2 秒）。macOS 上“刷文件 + 刷目录”实测中位 12 毫秒、95% 约 19 毫秒，已贴近保存 ≤ 20 毫秒的指标，P1 视基准结果决定是否改为批量刷盘。重命名前不能让任何人看到写了一半的文件。
- 选这种布局的理由：保存一次修改只写一个小文件（满足“保存 ≤ 20 毫秒”）；不同设备写不同的增量文件，以后同步没有文件级冲突；损坏只影响一个文件。

### 8.1 历史压缩

- P1 到 P3 **不做历史压缩**（Loro 的浅快照），保留完整历史：验证中一篇 2 万次输入的文章完整文档只有 86 KB。
- P4 引入同步时再启用压缩，规则先定下来：只能压缩到“所有设备都已确认的版本”之前；不压缩到仍有版本标签、或仍允许撤销的 AI 修订之前（或者先把那些版本的正文另存）。验证表明，压缩掉的历史一旦被离线设备的旧增量依赖，那份增量就再也无法合并。

## 9. 撤销 AI 修订

语义（已定）：把那次修改**反向应用到当前版本**；和后来的改动冲突时不应用，显示对比由我决定。不追求完全回到过去。

- 一个 AI 提议在条目文档里是一次提交（提交说明 `ai:<提议编号>`），所以能精确找到“AI 修改前”和“AI 修改后”两个版本。
- 计算反向修改：比较这两个版本，得到需要恢复的修改块。
- **冲突判断必须基于字符身份，不能只比较文字**：对每个修改块，用 Loro 的稳定位置检查 AI 写下的那些字符和它们左右各一个邻居现在是否还在、是否仍然相连。全部满足才映射到当前位置执行；任何一块不满足，整组都不应用，显示“AI 之前 / AI 之后 / 现在”三段对比。验证中只比较文字的版本静默产生了乱码。
- 撤销本身作为一次提交，提交说明 `revert:<提议编号>`，所以“撤销的撤销”也可以做。
- 富文本（格式、块）的完整实现估计 3 到 5 天，P3 和 AI 提议一起做。

## 10. 类型定义

- 每个类型一份 Loro 文档：`types/<h>/<类型编号>.dexm`，增量规则同第 8 节。
- 内置类型的编号是固定名字（`note`、`todo` 等），由软件在创建库时写入；自定义类型的编号是 UUIDv7。
- 布局（P1 定，2026-11-02）：`"dem"`、`"def"`（Map，只有一个键 `json`：整个类型定义的 JSON，含 name、builtin、default_view、default_privacy、color、fields）。类型很少改、不含内容，整段写最简单；两台设备同时改同一个类型时只留一边。
- 删字段、改字段类型时，已有条目里的数据不删除，只是不显示（M1）。

## 11. 关系

**已确认 2026-10-18**：**不设 `links/` 目录**，关系存在来源条目自己的文档里（M2 已同步）：

- 正文里的内链是 `body` 里的 `item_link` 节点（带目标编号），位置随正文移动。
- 正文之外的关系（属于、来源、推进、生成自、批注）存在条目文档的 `"links"` Map 里，键是关系编号（UUIDv7），值为 `{ to, kind, anchor? }`；`anchor` 是 Loro 稳定位置的编码字节。
- 反向链接不存，由索引从所有条目的这两处算出（M1 已规定）。

理由：关系和条目一起原子写入、一起同步、一起有历史，不需要为 `links/` 再设计一套合并规则；损坏也只影响一个条目。代价：查“谁指向我”必须靠索引（本来也是如此）。

## 12. 日志（活动记录、复习记录、AI 访问记录）

### 12.1 分段文件

`logs/<种类>/<yyyy-mm>/<设备>.dexl`，`<种类>` 为 `activity`、`review`（P3）、`ai-access`（P3）。每台设备每月一个分段，只追加。

```
分段头（32 字节）：
  0   4   魔数 "DEXL"
  4   2   封装版本（1）
  6   2   文件密钥编号
  8   24  分段盐（创建分段时随机生成，之后不变）
之后是记录，每条：
  0   4   后面部分的长度 n（u32）
  4   24  XChaCha20 随机数
  28  n-24  密文和认证标签
```

每条记录的附加认证数据 = 分段头 ‖ `0x00` ‖ 规范路径 ‖ `0x00` ‖ 记录序号（u64，从 0 开始）。

- 追加不需要重写文件；记录不能被挪到别的分段或别的位置。
- 崩溃留下的半条记录在读取时识别为“尾部截断”，丢弃即可，不算损坏；下次追加前先截掉它。
- 单条记录损坏只影响这一条，前后的记录照常可读。单条记录上限 16 MiB。

### 12.2 记录内容

每条记录的明文是一个 JSON 对象，公共字段：`v`（记录结构版本，当前 1）、`ts`（RFC 3339）、`kind`。**不记录正文、标题、搜索词和任何密钥。**

| 种类 | 字段 |
| --- | --- |
| `activity` | `item`、`type`、`action`（create / edit / move / state / delete / import / export）、`origin`（me / ai / import / system） |
| `review`（P3） | `item`、`rating`、`confidence`、`peeked`、`duration_ms`、`context`（M7 的 ReviewLog） |
| `ai-access`（P3） | `session`、`session_kind`（normal / sensitive_authorized）、`tool`、`items`（编号和隐私层级的列表）、`result`（returned / denied / not_found） |

AI 提议本身（编号、会话、每个字段修改前后的内容、理由、状态）是“提议”系统条目，存在条目文档里，不在日志里，因为它含有内容。

## 13. 附件（`.dexs`）

- 附件名 = `HMAC-SHA256(附件命名密钥, 附件明文)` 的小写十六进制（64 字符）。同一个库里同一个文件只存一份；外人无法拿一个已知文件算出名字来判断库里有没有它。
- 路径：`blobs/<h>/<附件名>.dexs`。附件不可变，不需要 CRDT。
- 分块加密，不需要把文件整个读进内存（STREAM 构造，RustCrypto `aead::stream` 的 32 位大端计数器加“最后一块”标记）：

```
头部（32 字节）：
  0   4   魔数 "DEXS"
  4   2   封装版本（1）
  6   2   文件密钥编号
  8   4   明文分块大小（u32，65536）
  12  19  随机数前缀
  31  1   保留，0
之后每块：min(分块大小, 剩余) + 16 字节；最后一块可以更短；空文件是一个空的最后一块
```

每块的附加认证数据 = 头部 ‖ `0x00` ‖ 规范路径。删块、换序、截断、改任意字节都会解密失败。

- 提取出的文字（PDF、幻灯片）存在“文件”条目的字段里，隐私层级和文件本身一致。

## 14. 本地索引

- `index.sqlite`，SQLCipher 4 默认参数（AES-256-CBC、HMAC-SHA512、4096 字节页），密钥是第 4.2 节的索引密钥。可以随时删除重建，不同步。
- 索引库里记录**索引版本** = 结构版本 + 分词规则版本 + 繁简折叠表版本（如 `schema-1/tok-1/opencc-1.4.1-chars-v1`）。版本和软件不一致时自动重建。
- 分词与繁简折叠规则见 `docs/spikes/02-search.md`，P1 写进 M3。
- **隐私（已确认 2026-10-18）**：普通、敏感、私密内容的标题和正文都进全文索引（索引本身加密，搜索是我自己用的）；**机密内容只索引元数据**（类型、状态、时间、标签以外的结构字段），标题和正文不进全文索引，所以搜索结果和摘要里不会出现机密内容的文字。

## 15. 隐私层级规则

| 层级 | AI 能否读取 | 后台任务（定期维护等） | 全文索引 | 其他 |
| --- | --- | --- | --- | --- |
| 普通 | 可以 | 参与 | 进入 | — |
| 敏感 | 只在我授权的会话里 | 不参与 | 进入 | 敏感授权会话里 AI 不能上网搜索和读网页；标了 `ai_web` 的条目可以出现在联网授权会话里（见下）；读取时界面有提示，并记入 AI 访问记录 |
| 私密 | 不可以 | 不参与 | 进入 | — |
| 机密 | 不可以 | 不参与 | 只有元数据 | 可选打开前再验证（建议）；以后同步时可设为只存本机 |

- **层级存在条目的 `meta.privacy` 里**，和内容一起加密、一起有历史。
- **联网授权（2026-10-19）**：敏感条目可以由用户本人标上 `meta.ai_web = true`，表示“这一条可以在开着上网的会话里给 AI 用”（比如专门放投递资料的一条）。三种会话：

  | 会话 | 上网 | AI 能读的敏感内容 |
  | --- | --- | --- |
  | 普通会话 | 开 | 无 |
  | 敏感授权会话 | 关 | 全部敏感内容 |
  | 联网授权会话 | 开 | 只有标了 `ai_web` 的敏感条目 |

  两种授权会话都要用户本人发起。`ai_web` 只能由用户在界面上设置并确认，随时可以撤回；AI 不能修改、也不能提议修改它和 `privacy`。对私密、机密内容，这个标记无效。缺省为否，所以已有的 v1 数据不受影响，不需要升级格式版本（P1 落地前的改动）。
- **继承**：在领域或项目上设置的层级作为新建下级内容的默认值；只影响新建，不批量改已有内容。
- **受限视图**：AI 网关只能拿到 `dem-core` 的受限视图。私密、机密内容在其中不可达；**“不可见”和“不存在”返回完全相同的结果**，AI 无法借此探测（P0-14 的网关已按此实现）。指向不可见内容的关系只显示“受保护的内容”。
- **导出**：完整导出包含所有层级（是我自己的数据）；密码库不在其中。
- **命令行**（P2）：默认不输出私密和机密内容，需要明确加参数。
- **日志**：任何日志都不记录正文、标题、搜索词和密钥；AI 访问记录只记编号和层级。

## 16. 已知的元数据泄露

拿到库文件（没有密码和恢复码）的人能看到：

- 文件的数量、大小和修改时间，因此大致能看出条目数量和活跃程度；
- 条目编号（UUIDv7）里的创建时间（精确到毫秒）；
- 设备编号和每台设备的增量序号；每台设备每月的日志大小；
- 附件的大小（但看不出是哪个文件）；
- `manifest.json` 里的库编号、创建时间和推导参数。

看不到：任何标题、正文、字段、标签、关系、类型名称、隐私层级和结构树。我认为这些泄露可以接受。

## 16.1 P4 新增（2026-11-03，已有的文件和文档布局都没变，格式版本仍为 1）

### 白板

白板是普通条目（类型 `whiteboard`）。节点和连线放在它的 `fields` 里：键是 `canvas:<编号>`，值是界面拥有的 JSON 文本，整条替换，所以两台电脑改不同的节点都能保留。节点 `{x, y, w, h, text?, item?, blob?, url?}`，连线 `{from, to}`。节点里的文字进搜索，`item` 算一条链接。

### 密码库 `vault/`

```
vault/vault.json        明文：format、salt、m_kib、t、p、nonce、wrapped
vault/<条目编号>.dexv    一条密码，整体封装（第 5 节），路径是附加数据
```

- 随机生成自己的主密钥，用 Argon2id 从密码库主密码推导的密钥包起来，算法和资料库一样（第 4 节）。附加数据绑定格式版本和推导参数。没有恢复码。
- 文件密钥用 HKDF 从密码库主密钥推出，盐是固定串 `dem/vault/key/v1`。和资料库的密钥没有任何关系。
- 每条一个文件，内容是 `{id, title, username, password, url, notes, updated}` 的 JSON。文件名只有随机编号。

### 同步

同步只传文件，不改文件。传 `items/ types/ structure/ logs/ blobs/ vault/`，第一次多传一份 `manifest.json` 用于加入。不传 `local/`、索引、`.lock`、`tmp/`。

- 每台电脑在 `local/` 里记着上次和存放处一致时每个文件的哈希，用它分辨谁改过、谁删过。
- **两边都改了同一个快照**：对方的版本解封后，用自己的设备编号和新序号重新封装成一个 `.dexu`，再把自己的快照传上去。快照可以当增量导入，所以两边的内容都在，由 CRDT 合并。
- **两边都改了同一条密码**：后同步的为准。
- **存放处丢了一半以上的已知文件（且超过 20 个）**：判断为选错位置或被清空，这一轮什么都不动。
- `manifest.json` 传上去后不再更新：每台电脑可以有自己的主密码，包的是同一个主密钥。
- 还没有压缩历史（第 8.1 节的规则留到以后）。

## 18. 校验规则（格式校验器逐项检查）

不需要密钥的检查：

1. `manifest.json` 存在、是合法 JSON、`format` 和 `format_version` 正确、必需字段齐全、参数在合理范围内。
2. 所有文件都在第 2 节列出的位置；没有多余的文件或目录（`tmp/` 除外）。
3. 文件名符合命名规则，分片目录与文件名的哈希一致。
4. 每个 `.dexm`、`.dexu` 的头部：魔数、版本、密钥编号在 `file_key_ids` 中、长度不小于 48 字节。
5. 每个 `.dexl` 的分段头合法，记录长度字段可以完整解析（尾部截断单独报告）。
6. 每个 `.dexs` 的头部合法，长度与分块规则一致。

需要密钥的检查：

7. 每个文件都能解密（附加认证数据含路径，所以位置不对的文件也会在这里被发现）。
8. 每个快照和增量都能被 Loro 导入；`dem.schema` 是支持的版本；`meta` 的必需字段齐全且取值合法；`meta.id` 隐含在文件名里，两者一致。
9. 结构文档：节点 meta 合法，引用的条目存在，项目没有下级项目以外的问题（只报告，不修复）。
10. 关系和内链指向的条目存在（不存在只报告为“悬空”，不算损坏）。
11. 附件：解密后重新计算附件名，与文件名一致。
12. 日志：每条记录能解密、是合法 JSON、含公共字段，且不含 `body`、`title` 等内容字段。

每项问题报告文件路径和类别；退出码：0 无问题，1 有警告（如悬空链接、尾部截断），2 有损坏。
