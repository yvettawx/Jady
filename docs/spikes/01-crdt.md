# P0-10 技术验证：CRDT 库与编辑器（Loro 对比 Automerge）

> 日期：2026-10-17 ~ 18。代码和原始数据：`spikes/crdt/`（复现命令见其中 `README.md`，原始输出在 `spikes/crdt/results/`）。
> 机器：Apple M1（8 核，16 GB），macOS（Darwin 25.6.0）；Rust 1.99.1，Node 26.10.0。
> **注意**：测试期间其他验证任务在同一台机器上并行运行，系统平均负载大多在 20 ~ 60（8 核），只有第 9 节第二轮的部分时段较空闲。所有耗时都偏慢且有波动，只适合做两个库之间的相对比较，不能当作最终性能指标。

## 要回答的问题

1. Loro 和 Automerge 哪个满足硬性要求（P0-10 第 1、2、5、7、10 项）？
2. 选中的库上，“撤销 AI 修订”（反向应用到当前版本，冲突时给出对比）能不能做、要做多少？
3. 选中的库对格式规范有哪些约束：文件布局（快照/增量）、历史压缩与将来同步、版本固定。

## 做法

两个库共用同一套测试代码：

- **编辑器（JS）**：真正的 ProseMirror `EditorView`（在 jsdom 上运行），分别通过官方绑定 `loro-prosemirror` 和 `@automerge/prosemirror` 连到 CRDT 文档。同一个 schema：加粗、斜体、代码、链接、标题，外加两个自定义节点——`item_link`（行内原子节点，带 `id` 和 `label` 属性）和 `mermaid`（代码块）。两份副本并发编辑 7 轮，然后按“各自缺什么就发什么”的方式交换增量。
- **核心（Rust）**：定义一个与库无关的接口（插入、删除、提交并记录来源、取版本、取历史版本正文、稳定位置、导出/导入），场景 3、4、5、6、8 是同一份代码分别跑两个库。场景 7（树）和 9（性能）各写一份。
- **互通（场景 2）**：JS 编辑器产出的字节交给 Rust 导入、核对正文、再由 Rust 修改（加粗文字 + 新段落，来源标记 `ai:rust-1`），把增量推回 JS 编辑器显示。另用 npm 别名装了多个旧版本做兼容矩阵。

使用的版本：

| | Loro | Automerge |
| --- | --- | --- |
| Rust | `loro` 1.16.2 | `automerge` 0.12.0 |
| JS/WASM | `loro-crdt` 1.16.2 | `@automerge/automerge` 3.5.0 |
| ProseMirror 绑定 | `loro-prosemirror` 0.4.4 | `@automerge/prosemirror` 0.2.0 |
| 兼容矩阵另测 | `loro-crdt` 0.16.12、1.0.9、1.5.13、1.10.8、1.16.4 | `@automerge/automerge` 2.1.13、2.2.9、3.0.0、3.2.6 |

ProseMirror：model 1.25.12、state 1.4.4、view 1.42.6、transform 1.12.2；jsdom 30.1.3；文本对比用 `similar` 2.7.0。

## 数据

### 1. 富文本与编辑器绑定（硬性）

两个绑定都能承载自定义节点（`item_link` 的 `id`/`label` 属性、`mermaid` 块），7 轮并发编辑后两份副本**全部收敛**，ProseMirror 文档全部通过 `check()`，保存后重新加载内容一致。

| 并发场景 | Loro | Automerge |
| --- | --- | --- |
| 各改各处（加粗、链接、代码、改 Mermaid、加内链、加段落） | 合理 | 合理 |
| A 加粗 “Hello”，B 在词中间插入 “XY” | `**HelXYlo**`，合理 | 同左 |
| A 加粗 “closing”，B 紧接着打 “!” | 感叹号不加粗，合理 | 同左 |
| 同一个词两人设了不同链接 | 取一方，合理 | 同左 |
| A 改内链显示名、B 改内链目标 id | 两个属性都保留，合理 | 同左 |
| **A 在段中回车分段，B 同时在段尾打字** | **B 打的字跑到了前一段**（`AAA  END`），没丢字但位置错 | 正确（`... BBB END`） |
| A 删除整个 Mermaid 块，B 同时在块内打字 | 整块删除，B 的字一起消失 | 块删了，B 打的字**并到了上一段末尾** |

其他发现：

- Loro 绑定把 ProseMirror 树原样映射成嵌套的 Map/List/Text；分段在 CRDT 里是“删掉后半段文字 + 新建段落重新插入”，所以和对方在后半段的并发输入合并时会错位。Automerge 绑定把整篇正文存成**一段带块标记的平面文本**，分段只是插入一个标记，所以这一项更好。
- 两个库都**不能在两台设备上各自初始化同一个空文档**：Loro 合并后丢了一方的字；Automerge 底层收敛了，但一个编辑器显示的内容和底层不一致。规则：文档骨架只由核心创建一次，其他副本一律从已有字节加载。
- Automerge 绑定会给节点加内部属性 `isAmgBlock`，两份编辑器的 JSON 因此不完全相同（显示和底层数据相同，无害）。
- 每轮并发编辑交换的增量：Loro 95 ~ 446 字节，Automerge 154 ~ 693 字节。Loro 的“空增量”也有 22 字节（只有头部）。

### 2. Rust 与 WebAssembly 互通（硬性）

| 检查 | Loro | Automerge |
| --- | --- | --- |
| Rust 导入 JS 编辑器字节，纯文本与编辑器一致 | 一致 | 一致 |
| Rust 修改（加粗文字 + 新段落）后增量推回编辑器并正确显示 | 是（253 字节） | 是（315 字节） |
| 编辑器读到 Rust 写的来源 `ai:rust-1` | 是 | 是 |
| 编辑器再改，Rust 导入编辑器的增量 | 是 | 是 |

版本不一致时（Rust 端固定为 Loro 1.16.2 / Automerge 0.12.0，JS 端换版本；每个版本都做了“导入 Rust 快照、导入 JS+Rust 增量、读来源、修改并导出快照和增量、再由 Rust 导入”）：

| JS 版本 | 结果 |
| --- | --- |
| loro-crdt 0.16.12（1.0 之前） | **读不了**，明确报错 “Encoding version 3 is incompatible … backward compatible but not forward compatible” |
| loro-crdt 1.0.9 / 1.5.13 / 1.10.8 / 1.16.2 / 1.16.4 | 全部双向通过 |
| @automerge/automerge 2.1.13 / 2.2.9 / 3.0.0 / 3.2.6 / 3.5.0 | 全部双向通过 |

**重要的反例**：让 Rust 1.16.2 用一个较新才有的功能（“可合并的子容器”，`ensure_mergeable_text`）写一个文档，Loro 1.0.9 / 1.5.13 / 1.10.8 **都能导入、不报错，但读出来的结构是错的**（字段值变成一串字节，多出一个奇怪的根键）。也就是说，旧版本遇到新功能时不是报错，而是**静默读错**。

Rust 端没有做“旧 Rust crate 读新字节”的测试（同一个 Cargo 依赖图里不能放两个兼容版本号的同名 crate）；JS 端的旧版本就是同一套 Rust 核心编译成的 WASM，可以代表这种情况。

### 3. 稳定位置（批注锚点）

锚在 “fox” 上的位置（编码后 Loro 12 字节、Automerge 13 字节，可存进别的条目），两个库结果完全相同：前面插入、前面删除、紧贴前后插入、另一副本的并发修改合并之后，**都仍然准确指向 “fox”**。锚定的词本身被删除时，位置落到相邻处——软件需要自己判断“锚点失效”并提示。

### 4. 历史版本

把两个版本号存进文档自己的 `labels` 列表（Loro 版本号 3 字节，Automerge 32 字节/每个头），保存、换副本加载后再读，两个历史版本的正文都正确。两个库都满足。

### 5. 修改来源元数据（硬性）

用每次提交的提交说明记录来源（`import`、`me`、`ai:g1`、`ai:g2`）。整份保存再加载、以增量形式导入空文档两种方式之后，来源全部读得回来；跨语言（JS 写、Rust 读和反过来）也都读得回来。两个库都满足。

差别：Loro 会把**同一设备上连续的、来源相同的**提交合并成一条记录（11 次 `me` 的按键合并成 1 条，来源不同的不会合并），Automerge 每次提交都是一条。

### 6. 撤销 AI 修订（按已定语义：反向应用到当前版本）

测试正文 “The quick brown fox …”，AI 一次修改：替换一个词组、删除一句、在末尾追加一句。

| 情况 | Loro | Automerge |
| --- | --- | --- |
| a. 之后没再改 | 正确恢复 | 正确恢复 |
| b. 之后改了别处 | 正确恢复且保留后来的修改 | 同左 |
| c. 之后改了同一处（在 AI 写的词里加逗号） | 识别为冲突，给出“AI 之前 / AI 之后 / 现在”三段对比，不改动正文 | 同左 |
| d. 别的设备改了别处，合并后再撤销 | 正确 | 正确 |
| e. 别的设备紧挨着 AI 删除处改了字 | 识别为冲突 | 识别为冲突 |
| 真实编辑器文档（加粗文字 + 新段落，之后用户改了标题） | 正确恢复（用 Loro 自带的差异变换） | 正确恢复（用通用算法） |

做法和教训：

- **通用算法**（两个库共用，约 120 行）：取 AI 修改前后两个版本的正文，算出反向的修改块；对每个块，用**稳定位置**（即 CRDT 内部的字符身份）检查“AI 版本里这些字符及左右各一个邻居，现在是否还在、是否仍然相连”。都在就映射到当前位置执行；否则算冲突。
- 第一版只用文字对比判断冲突，在情况 e 里**静默产生了乱码**（`The tSecond sentence here. hird`）。原因是文字对比看到的修改和 CRDT 实际的操作不是一回事。所以冲突判断**必须基于字符身份**，不能只比文字。
- Loro 另有原生做法：`diff(AI后, AI前)` 得到反向修改，再对 “AI 之后发生的一切” 做变换后应用（这正是 Loro 撤销管理器的内部做法），它能处理整棵嵌套树、格式和块。但它**不判断冲突**：情况 c 静默得到 `The ,quick brown`。另外变换函数只能通过 `doc.inner()` 拿到内部 crate 的类型，不在稳定的公开接口里。
- 结论：两个库都**需要自己写冲突判断**。正文是纯文字时工作量小（已有原型）；富文本里还要处理格式和块：Automerge 的平面文本模型可以直接套用通用算法（块标记就是一个字符，但恢复被 AI 删除的块要连属性一起恢复，格式要单独处理）；Loro 用原生变换做“应用”，冲突判断要按容器（每段文字、每个块的属性）分别做身份检查。估计富文本完整版 3 ~ 5 天（含测试），两个库差不多。

### 7. 结构文档：可移动树（硬性）

| | Loro（`LoroTree`） | Automerge |
| --- | --- | --- |
| A 移到 B 下 / B 移到 A 下，同时进行 | 合并后 A 在 B 下、B 在根下，**无环**，两边一致 | 原生没有树；用 “每个节点一个 parent 字段” 的朴素做法，合并后 **A↔B 成环** |
| 一边删除节点 C，另一边把 D 移进 C | 一致；D 随 C 一起被删除 | 未测 |
| 随机测试：3 副本、30 节点、300 轮随机并发移动 | 0 次成环、0 次分叉；本地会拒绝直接造成环的移动（179 次） | 自己写的“移动日志”方案：0 次成环、0 次分叉 |

Automerge 要满足这一项，必须自己实现一个移动算法（本次原型：所有移动记成带时间戳的追加日志，读取时按时间重放并跳过会成环的移动，约 120 行）。它能工作，但：日志永远增长、每次读取都要全量重放、和 Automerge 自身的历史压缩没有配合；原型跑这个随机测试用了 147 秒（Loro 9 秒，主要是我写的实现效率低，不全是库的问题）。按“不满足直接淘汰”的判断标准，**Automerge 在这一项上不满足**（需要自行实现一个正确性要求很高的算法）。

### 8. 体积：一篇文章逐字输入 2 万次

模拟打字（85% 插入、10% 退格、5% 跳到别处），最后正文 15,938 字（中英文混合，31 KB UTF-8）。随机字符的可压缩性比真实文章差，数字偏保守。

| 每次按键提交一次 | Loro | Automerge |
| --- | --- | --- |
| 历史里的修改记录条数 | 5（同来源连续提交被合并） | 20,001 |
| 完整文档（状态 + 全部历史） | 85,879 B（deflate 后 57,892） | 44,114 B（自带压缩） |
| 只有全部历史 | 55,086 B | 逐条增量拼起来 2,006,950 B |
| 去掉历史只留当前状态 | 35,044 B（浅快照）（deflate 后 26,052） | 20,485 B（只能重建一个新文档） |
| 加载完整文档 | 约 1 ms | 139 ms |
| 2 万次输入耗时 | 81 ms | 1,753 ms |

每 50 次按键提交一次时，Automerge 的修改记录降到 401 条、加载 34 ms，完整文档大小几乎不变（44,105 B）；Loro 基本不变。

**压缩后还能不能合并旧的增量**（第二台设备在第 1 万次输入时离线，做了修改，之后才带回来）：

| 压缩方式 | Loro | Automerge |
| --- | --- | --- |
| 只留当前状态 | **不能**，明确报错（依赖不在浅历史内） | **不能**（变成“缺依赖”挂起，永远应用不上） |
| 保留离线设备分叉点之后的历史 | 能（78,810 B） | 不支持部分压缩 |
| 保留更早（第 5 千次之后）的历史 | 能（82,834 B） | 不支持 |

### 9. 性能：1 万 / 5 万 / 10 万个小条目文档的加载（Rust，release 构建）

每个条目：meta（10 个字段，含 3 个标签）、fields（3 个字段）、正文约 600 字带两处格式、4 次提交。每份文档平均：Loro 快照 3,518 B（只存全部增量 1,717 B，浅快照 1,888 B），Automerge 1,715 B。

共跑了两轮，每轮每项 3 次（第一轮 2026-10-18 00:00 左右，平均负载 20 ~ 70；第二轮 04:30 ~ 06:30，开始时负载约 3，中途其他任务开始编译，负载回到 5 ~ 60）。下表的耗时取 6 次中最快的一次；内存是“峰值常驻内存减去加载前的常驻内存”（加载前已经把整份字节读进内存）。原始数据：`results/perf.jsonl`（第二轮）、`results/perf-under-load.jsonl`（第一轮）。

| 文档数 | 操作 | Loro 耗时 | Automerge 耗时 | Loro 额外内存 | Automerge 额外内存 |
| --- | --- | --- | --- | --- | --- |
| 1 万 | 逐个加载、读标题、丢弃 | 0.39 s（39 µs/份） | 3.4 s（344 µs/份） | 3 MB | 3 MB |
| 1 万 | 全部保持打开（读标题） | 0.38 s | 3.5 s | 452 MB（约 45 KB/份） | 213 MB（约 21 KB/份） |
| 1 万 | 全部保持打开（读正文） | 0.51 s | 3.7 s | 467 MB | 213 MB |
| 5 万 | 逐个加载、读标题、丢弃 | 2.0 s（39 µs/份） | 17.3 s（347 µs/份） | 3 MB | 3 MB |
| 5 万 | 全部保持打开（读标题） | 1.9 s | 30.6 s | 0.86 ~ 2.2 GB | 0.85 ~ 1.05 GB |
| 10 万 | 逐个加载、读标题、丢弃 | 2.5 s（25 µs/份） | 34.9 s（349 µs/份） | 4 MB | 3 MB |
| 10 万 | 全部保持打开（读标题） | 2.4 s | 22.1 s | 2.6 ~ 4.5 GB | 2.0 ~ 2.1 GB |
| 10 万 | 全部保持打开（读正文） | 3.2 s | 23.3 s | 3.9 ~ 4.6 GB | 2.1 GB |

- 加载耗时：Loro 稳定在每份 25 ~ 50 µs，约为 Automerge 的 **1/7 ~ 1/10**。10 万份都不常驻时，Loro 约 2.5 秒，Automerge 约 35 秒。
- 内存：每份打开的 Loro 文档约 45 KB，Automerge 约 21 KB（1 万份时最稳定的数字）。5 万份以上时内存数字波动很大，因为本机只有 16 GB，系统在压缩内存，这些只能看量级。
- 逐个加载、用完丢弃时两个库的内存都只多几 MB。
- 两轮之间的差异主要来自机器负载（同一项最慢的一次可达最快的 2 ~ 3 倍），两库之间的比例不受影响。

另测：Loro 从“全部增量”形式（而不是快照）加载 1 万份，约 170 ~ 190 µs/份，全部保持打开约 300 MB。

### 10. 格式稳定性、规范、许可证、维护（2026-10-18 查阅）

| | Loro | Automerge |
| --- | --- | --- |
| 格式稳定承诺 | 1.0 起格式稳定；库自己的报错信息写明 “backward compatible but not forward compatible”（新版读旧数据，旧版不保证读新数据）。实测 1.0.9 ~ 1.16.4 互通 | README：“In general we try and respect semver”；规范文档要求实现保留不认识的操作和列，以便新旧版本协作。实测 JS 2.1.13 ~ 3.5.0 与 Rust 0.12.0 互通 |
| 已有的“断代” | **1.9.0 移除了 0.x 格式的读取**，0.x 文档要先用 ≤1.8 的版本迁移 | 未发现 |
| 公开规范 | 有：仓库 `docs/encoding.md`，自称“normative wire-format reference”，2026-07-17 对照代码核实过；仓库里还有一个用 MoonBit 独立实现同一格式的项目（`moon/`） | 有：automerge.org 上的二进制格式规范，标注为 **draft**，2025-08-27 更新，声明与参考实现不一致时以实现为准 |
| 许可证 | MIT（`loro`、`loro-crdt`、`loro-prosemirror`） | MIT（`automerge`、`@automerge/automerge`、`@automerge/prosemirror`） |
| 核心仓库活跃度（2026-07-18 起 3 个月） | 93 次提交、12 位作者，最近一次 2026-10-17；6,226 星 | 146 次提交、8 位作者，最近一次 2026-10-15；6,662 星；两名全职维护者（README） |
| ProseMirror 绑定活跃度 | `loro-prosemirror`：3 个月内 6 次提交，最近 2026-08-22，版本 0.4.x | `automerge-prosemirror`：3 个月内 0 次提交，最近 2026-02-25，版本 0.2.0 |
| Rust 接口 | 一等公民，文档完整 | README 原话：Rust 接口 “low level and not well documented” |

## 结论

**建议选 Loro**（`loro` 1.16.x + `loro-crdt` 同版本 + `loro-prosemirror`）。

- 硬性要求：Loro 五项全部满足。Automerge 第 1、2、5、10 项满足，**第 7 项（可移动树）原生不满足**，要自己实现并长期维护一个移动算法，按判断标准淘汰。
- 撤销 AI 修订：两个库都可行、都需要自己写冲突判断；Loro 多一个能处理整棵树的原生“应用”能力（但属于内部接口）。
- 性能：小条目加载 Loro 快 7 ~ 10 倍（10 万份 2.5 秒对 35 秒，见第 9 节）；2 万次修改的长文加载 1 ms 对 139 ms。
- 体积：Automerge 小一半左右（它自带压缩）；Loro 的文件经过 deflate 后差距缩小到约 1.3 倍。可以接受，且可以在加密前统一压缩。
- 内存：每份打开的小条目 Loro 约 45 KB、Automerge 约 21 KB（第 9 节），10 万份全部常驻要好几 GB，所以核心**不能把所有条目常驻内存**，只缓存正在用的；逐个加载再丢弃时内存几乎不增加。

需要正视的 Loro 风险：

1. **分段与并发输入合并错位**（第 1 节）。单人多设备、AI 修改走提议队列的场景下很少触发，不丢字，可接受；记录在案，以后可向 `loro-prosemirror` 反馈。
2. **旧版本静默读错新功能**（第 2 节）。必须固定版本、限制可用功能（见下）。
3. **曾经移除过旧格式的读取**（1.9.0 移除 0.x）。需要有不依赖 Loro 的完整导出作为兜底。
4. 正文布局依赖 `loro-prosemirror` 的内部结构（`nodeName`/`attributes`/`children`），Rust 端要读写正文就要按这个结构来——等于把绑定的结构写进了我们的格式。

### 建议的条目文档逻辑布局（Loro）

```
LoroDoc（每个条目一份）
├─ "dem"    Map   { schema: 1 }                         格式内的逻辑版本，迁移用
├─ "meta"   Map   type, title, state, privacy, container, created, updated, time, place, source
│                 └─ "tags"  Map<标签, true>           当集合用：并发添加不会重复
├─ "fields" Map   类型专属字段；长文本字段用子 Text 容器，短值直接存
├─ "body"   Map   loro-prosemirror 结构（通过 containerId 指到根 "body"，已验证可用）
│                 nodeName / attributes(Map) / children(List<Map | Text>)
└─ "labels" List<Map { name, version: Frontiers 编码字节, created }>
```

- 标量字段直接存值，并发修改“较晚的为准”，被覆盖的值留在历史里——和 `03-modules.md` 的同步规则一致。
- 结构文档单独一份 `LoroDoc`：`"tree"`（`LoroTree`，开启分数索引排序），节点的 meta 存 `{ kind: domain|project, item: 条目编号 }`；名称放在各自的条目里，不放在树里。**删除领域用“归档”标记，不用树的删除**，因为一边删除、另一边同时移进来的节点会被一起删掉（第 7 节）。

## 对文档和格式的影响

需要写进 `docs/format-spec.md` 和 `02-architecture.md` 的：

1. **文件布局**：建议“快照文件 + 增量文件”。每个条目一个快照（Loro snapshot），编辑过程中把每批修改的增量（通常一两百字节）单独加密追加成小文件；空闲或关闭条目时合并成新快照、删除增量。实测导出快照不到 1 ms，所以“每次整份重写”也可行，二者择一要在 P1 结合加密和原子写入的开销再定。
2. **压缩（浅快照）规则**：只能压缩到“所有设备都已确认的版本”之前；同步元数据里要记录每台设备已确认的版本向量。压缩会丢掉被压掉部分的来源记录、该部分的版本标签和可撤销性，所以还要规定：不压缩到仍有版本标签、或仍允许撤销的 AI 修订之前（或者先把这些版本的正文另存）。
3. **版本固定**：Rust 端和界面端的 Loro **必须是同一版本**；加密封装头部之外，在文档里（`dem.schema`）或格式头部记录写入时的库版本。升级 Loro 视为格式变更：要有迁移测试（旧文件全部可读、新文件不能被旧软件静默读错）。**规定只使用 1.x 早期就有的容器类型**（Map、List、MovableList、Text、Tree），不用可合并子容器等新功能，除非经过格式升级。
4. **样式配置不存在文档里**：格式的扩展行为（加粗后紧接着打字是否延续）由每个运行时自己配置，Rust 核心必须和编辑器用同一份配置（从同一个 schema 定义生成），写进规范。
5. **设备/会话编号（peer id）**：同一个编号不能被两个同时写入的副本使用；核心和界面里的编辑器副本要用不同编号。编号的分配规则要写进规范。
6. **来源元数据**：用提交说明记录 `me`、`ai:<提议编号>`、`import:<批次编号>`、撤销时记 `revert:<提议编号>`；每个 AI 提议的编号必须唯一（同来源的连续提交会被合并）。是否记录提交时间（`set_record_timestamp`）要决定——按时间找历史版本需要它。
7. **撤销 AI 修订的设计**：反向修改 + 基于字符身份的冲突检查（不能只比文字）；冲突时整组不应用，显示三段对比，由我决定。AI 的一次提议在核心里作为**一次提交**应用，便于定位。
8. **骨架只创建一次**：新条目的根容器只由核心创建，其他副本从字节加载，不能各自初始化。
9. **兜底导出**：除了 Loro 字节，保留一种不依赖 Loro 的完整导出（正文 + 字段 + 历史版本的纯数据），应对 Loro 将来再次移除旧格式读取。Loro 自带的 JSON 格式增量导出可作为候选，本次**未测**。
10. **内存**：核心只缓存正在使用的条目文档，其他靠索引；第 9 节的“保持打开”数据说明不能常驻。
11. `02-architecture.md` 第 79 行和第 130 行的待决项可以改成“已定：Loro”（经你确认后改）；`03-modules.md` 里“每个条目的 CRDT 文档”一节按上面的布局补充 `dem` 和 `tags` 的写法。
