# P0-11 技术验证：SQLite 分词、繁简互通与 SQLCipher

> 日期：2026-10-17 ~ 18。代码：`spikes/search/`（复现命令见其中 `README.md`，原始输出在 `spikes/search/results/`）。
> 机器：Apple M1（8 核，16 GB），macOS 26.6.2；Rust 1.99.1。
> **注意**：测试期间其他验证任务在同一台机器上并行编译和运行，系统平均负载 17 ~ 100（8 核）。耗时数据偏慢、波动大（同一配置的 10 万条 p95 在两次运行中分别是 150 和 115 毫秒）。每个数字旁边都注明了当时的负载；正式指标以 P0-40 在空闲机器上的结果为准。
> **Windows 没有实际运行过**，见“未完成”。

## 要回答的问题

1. `rusqlite` 带 SQLCipher 能否不依赖系统 OpenSSL 编译？有没有不用 OpenSSL 的加密后端？Windows 上有什么风险？
2. 用 Rust 写的 FTS5 自定义分词器（拉丁按词；中文、西夏文按单字加相邻两字；去重音、统一大小写；繁转简）能否满足样例查询？需要多少 `unsafe`，怎样隔离？
3. 繁简转换用哪个库：纯 Rust 还是 OpenCC 原版绑定？
4. 高亮和摘要的位置是否正确？
5. 1 万、10 万条目的建索引时间、库大小、查询耗时是否达标（p95 ≤ 50 / 200 毫秒）？

## 做法

- 一个独立的 Rust 程序 `search-spike`，子命令：`check`（样例查询集 + 高亮 + 加密检查）、`converters`（转换库对比）、`bench`（合成数据基准）、`mkdb`/`querydb`（不同加密后端互相打开）。
- 分词器分成两层：`tokenizer.rs` 是纯安全代码（不碰 FFI），`fts5.rs` 是唯一含 `unsafe` 的模块，负责向 FTS5 注册。崩溃（panic）不会穿过 FFI 边界。
- 索引表：`items(id, title, body)` 加外部内容的 FTS5 表 `items_fts(title, body, tokenize='dem')`；整个库用 SQLCipher 加密，密钥是 32 字节原始密钥（`PRAGMA key = "x'..'"`，跳过 SQLCipher 自带的 PBKDF2，因为索引密钥将来由 `dem-crypto` 从主密钥派生）。
- 合成数据：确定性随机（固定种子），按 Zipf 分布抽词，语言比例：简体 35%、繁体 15%（用 OpenCC 词组级转换生成）、西夏文（夹中文注释）5%、法语 15%、英语 30%。平均每条约 1400 字符（UTF-8 约 2.1 KB）。
- 用户输入一律转成带引号的 FTS5 字符串（每个空格分隔的词一个，隐式 AND），用户无法注入 FTS5 查询语法。

## 数据

### 1. SQLCipher 与加密后端

| 后端 | 怎么编译 | macOS 结果 | Windows |
| --- | --- | --- | --- |
| **OpenSSL（源码内置）**：feature `bundled-sqlcipher-vendored-openssl` | 从源码编译 OpenSSL 3.6.3，需要 perl | 通过：`check` 全部通过；可执行文件不依赖任何 OpenSSL 动态库 | 未运行。需要 Strawberry Perl（Git 自带的 MSYS perl 不行，会生成 Unix 路径）和 VS 的 `nmake`；`nasm` 可选，没有时 OpenSSL 编成 `no-asm`（AES 变慢）。在 macOS 上 `cargo check --target x86_64-pc-windows-msvc` 在 OpenSSL 的配置步骤失败（“This perl implementation doesn't produce Windows like paths”），这是交叉编译的限制，不代表在 Windows 上不行 |
| **CommonCrypto（苹果系统库）**：feature `bundled-sqlcipher` | 不需要 OpenSSL，链接 Security 框架 | 通过 | 不可用：`libsqlite3-sys` 在 Windows 上没有 OpenSSL 时直接报错 |
| **libtomcrypt**：`sqlcipher-src` 的源码 + 自写的小构建程序 `tomcrypt/`，再用 rusqlite 的非内置 `sqlcipher` feature 链接 | 只要 C 编译器，没有 perl、OpenSSL | 通过：`check` 全部通过 | 理论上最省事（只需 MSVC），未验证。需要自己维护一段构建代码（约 50 行），`sqlcipher-src` 是个人维护的小 crate |

- 三种后端产生的库文件**可以互相打开**（OpenSSL 建的库用 CommonCrypto、libtomcrypt 都能读，反之亦然），因为都是 SQLCipher 4 的默认参数（AES-256-CBC、HMAC-SHA512、4096 字节页）。
- 加密检查：库文件里搜不到明文（“独角兽”“Paris”“SQLite format 3”“items_fts”都不出现）；错误密钥打开报 `file is not a database`；正确密钥重新打开查询正常。
- 加密开销（1 万条，负载约 25 ~ 30）：建索引 4.4 秒（明文）对 5.2 ~ 10 秒（加密）；库大小 54.0 MB 对 57.9 MB；查询 p95 9.7 毫秒对 9.0 ~ 13.8 毫秒（在噪声范围内）。

### 2. 分词器

规则（实现见 `tokenizer.rs`）：

- **表意文字**（中文含扩展 A~J 和兼容汉字、西夏文 U+17000~187FF 与部件和补充、契丹小字、女书、假名、谚文）：建索引时每个字是一个词元；相邻两字的“双字”词元和前一个字放在**同一位置**（FTS5 的 colocated 标记）。
- **查询时**：单个字只查单字；两个字以上查“双字 + 双字 + … + 最后一个字”组成的短语。
  - 为什么末尾要多一个单字：FTS5 的高亮函数会**忽略同一位置的附加词元**，只看每个位置的第一个词元。如果短语以双字结尾，高亮只会标到最后一个双字的第一个字，漏掉最后一个字。实测只用双字时：样例高亮 4/9 正确、随机高亮 1961/3000 正确；加上末尾单字后全部正确。
- **其他字母和数字**：按词切分；纯 ASCII 直接转小写；否则 NFKD 分解、去掉组合附加符号、Unicode 完整大小写折叠（ß → ss，全角 ＡＢＣ → abc）。
- **繁转简**：逐字折叠（见第 3 节为什么不用词组级转换）。日文汉字也会被折叠（東 → 东），这是有意的。

样例查询集 `spikes/search/data/sample_queries.json`（22 篇文档、56 条查询、9 条高亮）：

| 检查 | 结果 |
| --- | --- |
| 56 条查询的命中集合完全一致（中文单字、两字、多字短语，繁简互搜，港台异体，西夏文单字/两字/四字，CJK 扩展 B，兼容汉字，法德重音，大小写，全角，中英混排，反例） | 56/56 |
| 9 条高亮字符串完全一致（含繁体文档被简体查询命中、西夏文、补充平面字符、法语重音） | 9/9 |
| 长文档中段的摘要包含完整的 `⁅独角兽⁆` | 通过 |
| 随机高亮：300 篇混合文字的合成文档，3000 个随机子串查询；去掉标记后原文不变，且有一段标记恰好覆盖查询 | 3000/3000 |

三个加密后端下结果相同。

### 3. 繁简转换库

样例 `spikes/search/data/converter_samples.json`：简→繁 83 句（集中在一对多：发/發/髮、后/後、干/乾/幹、只/隻、系/係/繫、复/復/複/覆、台/臺/颱/檯、里/裏、面/麪、松/鬆、制/製 等），繁→简 30 句（含简体保留“繁体样子”的字：乾隆、乾坤、著名、慰藉，以及港台异体）。港台异体先统一再比较（裡/裏、麵/麪、著/着 视为相同）。速度在 2 MB 合成文本上测（负载约 20 时的一次结果，波动很大）。

| --- | ---: | ---: | ---: | ---: | ---: | --- | --- | --- |
| `ferrous-opencc` 0.4.0（纯 Rust，OpenCC 词典） | 2 ms | 81/83 | 28/30 | 12 | 18 | 简→繁 62（0.009%），繁→简 1 | Apache-2.0 | 纯 Rust，无风险 |
| OpenCC 1.4.1 原版（`opencc-sys`） | 47 ms | 81/83 | 28/30 | 29 | 50 | —（基准） | 绑定 MIT/Apache，词典 Apache-2.0 | 需要 CMake、C++ 编译器、libclang（bindgen）；macOS 首次编译约 1.5 分钟 |
| `zhconv` 0.4.2（只开 OpenCC 词表） | 35 ms | 78/83 | 24/30 | 137 | 151 | 69 / 1209 | 代码 MIT/Apache；默认的 MediaWiki 词表是 **GPL-2.0+** | 纯 Rust（依赖 zstd-sys，需 C 编译器） |
| `fast2s` 0.3.1（只有繁→简） | 0.1 ms | — | 29/30 | — | 121 | 14 | MIT | 纯 Rust |
| `character_converter` 2.1.5 | 59 ms | 65/83 | 27/30 | 27 | 27 | 13021（2%） | MIT | 纯 Rust |
| 本验证的逐字折叠表 | 1 ms | — | 25/30 | — | 85 | 19 | 词典 Apache-2.0 | 纯 Rust |

- `ferrous-opencc` 与 OpenCC 原版在样例上**输出完全相同**，大语料上只有极少数分词边界不同（如“未来复杂”）。两者共同的错误：“衣服已经干了”“干杯”转成“幹”；“看著”（台湾写法）和“衞生”（香港写法）在标准繁→简配置里不转换（要用 `tw2s`、`hk2s` 配置）。
- 繁→简的“正确率”对搜索不重要，重要的是**同一个字在文档里和在查询里折叠成同一个结果**。词组级转换做不到这一点：文档里的“乾隆”保持“乾隆”，用户单独搜“乾”时被转成“干”，就搜不到了。所以索引用的是**逐字、与上下文无关的折叠表**：取 OpenCC `TSCharacters` 每个繁体字的第一个简体对应（3222 条），再加港台异体反查（10 条，如 衞→卫、綫→线；另有 49 个异体本身就是简体常用字，如 台、才、只，不折叠）。
- 逐字折叠的代价（都是“多搜到”，不会“搜不到”）：後/后、髮/發、乾/幹 都合并，所以搜“後”也会命中“皇后”，搜“髮”也会命中“发展”；“著名”被索引为“着名”（因此台湾的“看著”能被“看着”搜到）。
- 逐字折叠漏掉的情况（会“搜不到”）：“瞭解”不等于“了解”、“藉口”不等于“借口”，因为 瞭、藉 本身也是简体字。数量很少，可以将来用一张小的补充表处理。

### 4. 基准

查询集 33 条：中文高频单字、罕见字、两字词、长短语、繁体、西夏文单字（高中低频）/两字/三字、法语重音、英语、多词 AND、混合、未命中。每条先预热一次，再测 20 次。“排序查询”是界面会用的形式：`ORDER BY rank LIMIT 20` 加标题高亮和正文摘要。另测了“不排序、取前 20 条”和“只计数”。

- 慢的都是命中数极多的查询：10 万条里“发”命中 47561 条，排序查询 p95 218 毫秒；“理发店”命中 40509 条，p95 163 ~ 316 毫秒。耗时几乎全花在给所有命中打分排序（bm25）上，不排序取前 20 条只要 2 ~ 4 毫秒。
- 合成数据只有约 330 个中文词，词频远比真实文本集中（“头发”出现在 29% 的文档里），所以这是**偏悲观的**估计。但真实库里“的”“是”这类单字查询同样会命中大多数条目。

| 变体 | 库大小（10 万） | 建索引（10 万） | 排序 p95（1 万 / 10 万） | 短语计数“理发店”（10 万） |
| --- | ---: | ---: | --- | ---: |
| 单字 + 双字（推荐） | 580 MB | 128 秒 | 9 ~ 14 / 115 毫秒 | 18.6 毫秒 |

## 结论

1. **SQLCipher**：默认用 `bundled-sqlcipher-vendored-openssl`（rusqlite 官方支持、用户最多）。macOS 实测可用。Windows 需要 Strawberry Perl + MSVC，由 CI 首次验证。**备选**：如果 Windows CI 上 OpenSSL 编译出问题，换成 libtomcrypt 后端（本次已在 macOS 跑通，库文件与 OpenSSL 版互通），代价是自己维护一小段构建代码。CommonCrypto 只在 macOS 可用，不建议为了一个平台分两套后端。
2. **分词器**：按本文第 2 节的规则实现，样例全部通过。**查询必须在双字短语末尾加最后一个单字**，否则高亮和摘要会少标一个字。建议保留双字索引（真实文本中更有区分度），但这是可以以后改的决定：索引可重建。
3. **繁简**：索引用**逐字折叠表**（从 OpenCC 词典生成，随代码一起发布，带版本号），不用词组级转换。需要展示性的繁简转换时（比如以后的导出或界面显示）用 `ferrous-opencc`：纯 Rust、Apache-2.0、与 OpenCC 原版结果几乎一致、Windows 无编译风险。不用 OpenCC C++ 原版（Windows 要 CMake + libclang，没有收益）；不用 `zhconv` 默认配置（GPL 词表）。
4. **高亮与摘要**：FTS5 自带的 `highlight()`、`snippet()` 在这套分词器下位置正确（含补充平面字符和繁简不同的原文）。
5. **性能**：两档都达标，但 10 万条的高频词查询已经接近指标。建议 `dem-index` 的搜索分两步：先用不排序的查询立刻给出前 20 条（几毫秒），同时计算排序结果；或对命中数超过某个阈值的查询改用更便宜的排序（如按修改时间）。这留到 P1 实现，P0-40 在空闲机器上再测。

### `unsafe` 的隔离（建议）

- 需要的 `unsafe` 只有三类：用 `SELECT fts5(?1)` + `sqlite3_bind_pointer` 取 `fts5_api` 指针（rusqlite 没有封装）；调用 `xCreateTokenizer` 注册；三个 `extern "C"` 回调（把原始指针转回 Rust 引用、由 `(pText, nText)` 构造切片、调用 `xToken`）。共约 150 行，全部在 `fts5.rs`。
- 建议在 `dem-index` 里保持工作区的 `unsafe_code = "deny"`，只给一个文件开例外：`#[allow(unsafe_code)] mod fts5_ffi;`。配套规则：每个 `unsafe` 块必须有 `// SAFETY:` 说明（对 `dem-index` 开启 clippy 的 `undocumented_unsafe_blocks = "deny"`）；`cargo xtask check-layers` 增加一条检查：整个工作区里 `allow(unsafe_code)` 只允许出现在 `crates/dem-index/src/fts5_ffi.rs`；回调里一律 `catch_unwind`，失败返回 `SQLITE_ERROR`；分词逻辑本身留在安全代码里，单独做单元测试和随机化测试。
- 这需要你确认，因为它改动了“全工作区禁止 unsafe”的规则。

## 对文档和格式的影响

- `02-architecture.md` 第 3 节“繁简转换：OpenCC 词库”建议改为：“索引用由 OpenCC 词典生成的逐字折叠表；展示性转换用 `ferrous-opencc`”。“本地索引：SQLite + FTS5 + SQLCipher”维持不变，补充加密后端：内置 OpenSSL，备选 libtomcrypt。
- `03-modules.md` M3“繁简互通：建索引和搜索时都用 OpenCC 转成同一种写法”建议改为“逐字折叠”，并写明会多搜到（後/后 合并）和少数搜不到（瞭解/了解）的情况；查询规则写明“双字短语 + 末尾单字”。
- 格式规范：索引是可重建的本机文件，不属于同步格式，但建议记录一个**索引版本号**，由分词规则版本 + 折叠表版本（本验证为 `opencc-1.4.1/ts-chars+hk-tw-variants-rev/v1`）+ 结构版本组成。版本不一致时自动重建。索引密钥：由主密钥派生的 32 字节原始密钥直接交给 SQLCipher（跳过它自带的 PBKDF2），用途标签写进密钥体系一节。
- 库大小：索引表里存了一份正文副本（10 万条时正文 216 MB，占库的约 37%）。如果不想在索引里重复存正文，可以用 FTS5 的“无内容”表，但那样就不能用 `highlight()`/`snippet()`，要在 Rust 里自己做高亮。建议先保留副本（索引本来就是加密的），P1 再看。
- 隐私：索引里有正文副本，所以“私密/机密内容是否进索引”必须在格式规范的隐私一节写明（M3 已说密码库不进索引）。
- 搜索评测集（P0-37）可以直接以 `data/sample_queries.json` 为种子，格式：文档、查询（含期望的命中集合和类别）、高亮期望。
